1. VISÃO GERAL: MONÓLITO LOCAL

O Mello é um programa só, que guarda tudo num arquivo só, num único computador com Windows:

    ┌──────────────── Mello (um programa só) ────────────────┐
    │   Tela (React)  ──►  Lógica + acesso ao banco (main)    │ ──►  mello.db
    └─────────────────────────────────────────────────────────┘      (um arquivo no PC)

- Um usuário, uma máquina. Sem servidor, login, sincronização nem rede.
- Os mesmos dados aparecem no quadro Kanban e no calendário.
- Não precisa de: API REST, controle de usuários, microsserviços, Docker, banco em servidor,
  sincronização nem preocupação com escala (mesmo com milhares de cards o SQLite responde na hora).
- Continua importante: backup (o disco é o único lugar onde os dados existem), separar a tela dos
  dados, migrações do banco sem perda e a segurança básica do Electron.

Princípios
1. Simplicidade: uma camada ou ferramenta só entra se resolver um problema real deste app.
2. Os dados do usuário vêm primeiro: backup antes de migrar, backups automáticos e exportação em
   formato aberto.
3. Tipagem de ponta a ponta: o mesmo contrato TypeScript vale do banco até a tela.


2. PROCESSOS E CAMADAS

    Tela (React)  →  window.mello (preload)  →  ipc/ (Zod)  →  modules/  →  SQLite
                                                   ↑
                              agendador (main) ────┘  → avisa a tela: "data:changed" (etapa 8)

Camada     Onde roda               Faz                                      Pode acessar
---------  ----------------------  ---------------------------------------  -------------------
renderer   Chromium, em sandbox    Telas, interação, estado da interface    só window.mello
preload    ponte isolada           Expõe window.mello (uma função por       ipcRenderer, sem
                                   canal) pelo contextBridge                expô-lo à tela
main       Node.js                 Janela, ciclo de vida, banco, arquivos,  tudo
                                   backup, protocolo de arquivos
shared     importado pelos três    Tipos, contratos do IPC, Result, regras  nada (código puro)
                                   puras

Regra de dependência: main, preload e renderer podem importar de shared. O renderer nunca importa
de main, e shared não importa de ninguém. O preload importa só tipos e constantes de shared (roda
em sandbox, sem bibliotecas).

Dentro do main, a direção é uma só: ipc/ → modules/ → db/.
- ipc/: valida a entrada com Zod, chama o módulo e devolve um Result. Sem regra de negócio.
  routes.ts é a tabela de canais (não importa o Electron); index.ts só registra as rotas no
  ipcMain.
- modules/: regras e consultas de um assunto (um arquivo por assunto). Não conhece o Electron, por
  isso é testado com um banco em memória.
- db/: conexão, pragmas, schema e migrações.

4. INICIALIZAÇÃO (src/main/index.ts)

Antes de o app ficar pronto:
1. Define a pasta de dados (seção 9) e registra o esquema mello-arquivo como privilegiado.
2. Pede o bloqueio de instância única: abrir o Mello de novo só traz a janela atual para a frente.

Quando o app fica pronto:
3. Remove o menu da janela e liga o tema escuro do Windows (a escolha de tema entra na etapa 10).
4. Cria as pastas de dados e o arquivo de log.
5. Abre o banco (src/main/db/open.ts): se houver migração pendente num banco que já tem dados, faz
   um backup antes (DAD-01) e então migra.
6. Recusa todas as permissões do navegador, registra o protocolo de arquivos e os canais de IPC.
7. Cria a janela (1440 × 900, ou menor se a tela for menor; mínimo 1024 × 640).

Se algo falhar na abertura (por exemplo, um banco criado por uma versão mais nova do Mello), o erro
vai para o log, aparece um aviso "Não foi possível abrir o Mello" e o app fecha sem mexer no banco.

Ao fechar a última janela o app encerra e fecha o banco. A bandeja do Windows, que mantém o app
vivo para lembretes e repetições, entra na etapa 8 (P4).


5. BANCO DE DADOS

Detalhes das tabelas, índices e migrações: Docs/Modelo-de-Dados.txt.

- better-sqlite3 (síncrono) + Drizzle ORM. Cada consulta leva frações de milissegundo no volume de
  um uso pessoal, então o código síncrono no main é aceitável e bem mais simples.
- Pragmas na abertura: journal_mode = WAL, synchronous = NORMAL, foreign_keys = ON.
- Função unaccent registrada no SQLite, para a busca ignorar acentos (BUS-01):
  WHERE lower(unaccent(titulo)) LIKE lower(unaccent(?)).
- Migrações: geradas pelo drizzle-kit (npm run db:generate) e aplicadas pelo próprio app
  (src/main/db/migrate.ts). Os .sql entram no código do app no build, então o app instalado não
  depende de uma pasta de migrações ao lado do executável. O que já foi aplicado fica na tabela
  _migrations. Tudo roda numa transação, com as chaves estrangeiras desligadas durante a troca e
  conferidas (foreign_key_check) antes do commit, como recomenda a documentação do SQLite.
- Um banco com migrações que o app não conhece (de uma versão mais nova) é recusado.


6. COMUNICAÇÃO ENTRE A TELA E O MAIN (IPC)

- Os canais seguem o padrão entidade:ação (boards:list, cards:move…). Lista completa prevista:
  PLANO.md, seção 4. Existem hoje: app:info; boards:list, listClosed, get, create, update, move,
  close, reopen, delete, archived; lists:create, update, move, copy, moveToBoard, archive,
  archiveCards, restore; cards:restore e cards:delete.
- Mover (quadro ou lista) recebe o índice final entre os itens visíveis, e o main calcula a
  posição a partir do banco. Assim a tela nunca manda uma posição velha, e listas arquivadas ou
  quadros fechados no meio não atrapalham.
- Todo canal é requisição e resposta (invoke/handle).
- A resposta é sempre um Result:
      { ok: true, data }  ou  { ok: false, error: { code, message, details? } }
  Códigos: INVALID_INPUT (o Zod recusou a entrada), NOT_FOUND, CONFLICT, INTERNAL.
- src/main/ipc/handler.ts (createHandler): valida a entrada com o schema Zod, chama a função do
  módulo e transforma o retorno em Result. Um AppError lançado pelo módulo vira Result com o mesmo
  código e mensagem; qualquer outro erro vira INTERNAL e vai para o log.
- A tela usa unwrap() (src/renderer/src/lib/api.ts), que devolve o valor ou lança ApiError, que é o
  que o TanStack Query espera.

Exemplo (como os canais das próximas etapas serão escritos):

    // src/shared/ipc/api.ts — contrato
    export const CHANNELS = { appInfo: 'app:info' } as const
    export interface MelloApi { app: { info(): Promise<Result<AppInfo>> } }

    // src/shared/ipc/api.ts — o mesmo mapeamento serve ao preload e aos testes
    export function createApi(invoke): MelloApi { ... boards: { list: call(CHANNELS.boardsList) ... } }

    // src/preload/index.ts — ponte
    contextBridge.exposeInMainWorld('mello', createApi((ch, input) => ipcRenderer.invoke(ch, input)))

    // src/main/ipc/routes.ts — valida, chama, embrulha
    route(CHANNELS.boardsCreate, createBoardInput, ({ title }) => boards.create(db, title, now()))

    // na tela
    useQuery({ queryKey: queryKeys.boards, queryFn: () => unwrap(api().boards.list()) })


7. TELA (RENDERER)

Rotas (HashRouter, porque o app instalado carrega a tela por file://):

    #/                          Início (menu lateral: Quadros, Calendário, Configurações)
    #/calendar                  Calendário de todos os quadros (CAL-02)
    #/boards/:boardId           Quadro, com a barra flutuante de baixo
    #/boards/:boardId/calendar  Calendário do quadro, com a barra flutuante
    #/settings                  Configurações ("Voltar" leva para a tela de onde veio)
    qualquer outro              volta ao Início

Layouts (src/renderer/src/app/Layouts.tsx): HomeLayout (cabeçalho + menu lateral), BoardLayout
(cabeçalho + conteúdo + barra flutuante) e SettingsLayout (cabeçalho com "Voltar").

Cabeçalho de 56 px, em três variações, como no protótipo:
- home (Início e calendário de todos): busca "Pesquisar cards, tarefas e quadros", com a borda
  mais clara, e a engrenagem cheia;
- board (quadro e calendário do quadro): busca "Pesquisar" e a engrenagem de raios;
- settings: só o logo e o "Voltar".
O botão "Criar" abre o menu (Criar quadro; card e modelo nas etapas 3 e 11). A busca ganha
função na etapa 11.

Estado:
- Dados do banco: TanStack Query, com staleTime infinito e sem recarregar ao focar a janela. Os
  dados só mudam quando o próprio app os altera, e então a chave correspondente é invalidada.
  Chaves (lib/queryKeys.ts): ['boards'] (abertos), ['boards', 'closed'], ['board', id] (quadro
  com as listas) e ['board', id, 'archived'].
- Ações (lib/queries.ts, useAction): chamam o main, invalidam as chaves afetadas (mesmo se
  falharem, para a tela voltar ao estado real) e, em caso de erro, mostram o aviso no canto da
  tela (components/Notify.tsx).
- Arrastar listas e quadros atualiza o cache na hora (otimista) e depois confirma no main.
- Estado de interface: useState (Zustand entra quando houver estado compartilhado).
- Estado na URL: o quadro e a tela abertos.

Menus, confirmações e arrastar:
- Popovers (components/Popover.tsx): atributo popover nativo do navegador, aberto pelo botão com
  popoverTarget. O navegador cuida da camada de cima, do Esc e do clique fora; o posicionamento
  por âncora (position-area, com troca de lado quando falta espaço) prende o popover ao botão.
  O conteúdo só existe enquanto o popover está aberto, então submenus ("Mover lista", "Itens
  arquivados", "Criar quadro") recomeçam do zero a cada abertura.
- Confirmação (components/Confirm.tsx): um <dialog> modal único, no topo do app, com
  closedby="any" (Esc ou clique fora cancelam). Abrir o modal fecha os popovers, por isso ele não
  mora dentro deles; os componentes pedem a confirmação por useConfirm().
- Arrastar (dnd-kit, components/dnd.ts): mouse com 5 px de distância antes de começar (o clique
  continua funcionando) e teclado (espaço pega e solta, setas movem, Esc cancela; o Enter fica
  livre para abrir o quadro). Avisos para leitor de tela em português. A lista se arrasta pelo
  cabeçalho; o título e o botão "…" dentro dele não iniciam o arraste.

Navegador único: o app só roda no Chromium do Electron fixado no package.json (hoje o 152). Por
isso recursos novos da plataforma (popover, posicionamento por âncora, <dialog closedby>) são
usados direto, sem polyfill, depois de conferidos nessa versão. Ao atualizar o Electron, o
script de capturas mostra se algo mudou.

Estilo:
- CSS Modules por componente, usando as variáveis das paletas do protótipo
  (src/renderer/src/styles/themes.css). A classe tema-escuro ou tema-claro vai no <html>.
- A paleta é a união das variáveis de todas as telas do protótipo, sem alterar nenhum valor
  (TEM-02). Onde o protótipo só mostra o tema escuro (Início, calendário), o tema claro usa a
  variável clara equivalente.
- Fonte Inter local (@fontsource/inter, pesos 400 a 700, latin e latin-ext).
- Ícones: SVGs copiados do protótipo (components/Icon.tsx); o logo é o SVG literal do protótipo
  (components/Logo.tsx).


8. ARQUIVOS: PROTOCOLO mello-arquivo://

Imagens de fundo, capas e anexos ficam em <pasta de dados>\arquivos\<sha256>.<ext> (etapas 5 e 9).
A tela os carrega por:

    mello-arquivo://arquivos/<sha256>.<ext>

O protocolo (src/main/protocol.ts) só entrega um arquivo se o endereço tiver exatamente esse
formato: host "arquivos", nome com 64 caracteres hexadecimais minúsculos, um ponto e uma extensão
simples. Qualquer outra coisa (.., barras, caminho absoluto, codificação com %, outro host, porta
ou usuário) vira 404. Depois de montar o caminho, ele ainda confere que o arquivo está direto na
pasta de arquivos.


9. ONDE FICAM OS DADOS

- App instalado: %APPDATA%\Mello (mello.db, arquivos\, backups\, logs\).
- npm run dev: %APPDATA%\Mello-dev, para o desenvolvimento nunca mexer nos dados reais (decisão de
  21/10/2026).
- MELLO_DATA_DIR: variável que aponta para outra pasta. Só vale fora do app instalado; o script de
  capturas a usa com uma pasta temporária e dados fictícios.
- Logs: <pasta de dados>\logs\main.log (electron-log), só eventos técnicos, nunca o conteúdo dos
  cards.
- Backups: <pasta de dados>\backups\mello-AAAA-MM-DD_HHmm.db (DAD-02). Na etapa 1 só existe o
  backup antes de migrar; o automático, a rotação e a restauração entram na etapa 10.


10. SEGURANÇA

O Mello não carrega nada da internet. A segurança é o básico do Electron, ligado por padrão:
- contextIsolation, sandbox e nodeIntegration desligado na janela.
- O preload expõe funções específicas, nunca o ipcRenderer inteiro.
- Política de segurança (CSP) no index.html: default-src 'self'; script-src 'self';
  style-src 'self' 'unsafe-inline'; img-src 'self' data: mello-arquivo:; font-src 'self' data:;
  connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'.
  O 'unsafe-inline' de estilos é o que o Vite usa em desenvolvimento; scripts de fora não rodam.
- A janela não navega para fora do app, não abre janelas novas, e links https vão para o navegador
  padrão.
- Todas as permissões do navegador (câmera, microfone, notificações web…) são recusadas. Os
  lembretes usam a notificação nativa do main (etapa 8).
- Sem menu na janela. No desenvolvimento, F12 abre as ferramentas de desenvolvedor.
- O HTML da nota e da descrição é filtrado no main antes de salvar (NOT-04, etapa 4 e 5).

Ficam de fora, por não haver ameaça correspondente num app pessoal e offline: Electron Fuses,
assinatura de código e verificação do remetente de cada mensagem de IPC.


11. DATAS E HORÁRIOS

- Datas de entrega e de tarefas são "horário de relógio" local, sem fuso: "2026-10-20" (dia
  inteiro) ou "2026-10-20T14:30". Não há conversão para UTC, o que evita o prazo de dia inteiro
  que "pula" para o dia anterior.
- Esses textos ficam em ordem cronológica quando comparados como texto, então a consulta de um mês
  é só due_at >= '2026-10-01' AND due_at < '2026-11-01'.
- Campos de auditoria (created_at, updated_at, *_at numéricos) são instantes: epoch em
  milissegundos (UTC).
- O "agora" sempre chega por parâmetro às regras e aos módulos, para os testes controlarem o
  relógio.
