1. COMO RODAR

npm test ............... todos os testes, uma vez (Vitest)
npm run test:watch ..... roda de novo a cada alteração
npx vitest run --project main ....... só os testes do main e do shared (Node)
npx vitest run --project renderer ... só os testes da tela (jsdom)
npm run capturas ....... abre o app de verdade e salva as capturas (seção 4)

Os testes rodam no Node 24 do computador. O better-sqlite3 13 traz um binário N-API que serve tanto
ao Node quanto ao Electron, então o banco real abre dentro do Vitest sem recompilar nada.


2. ONDE FICAM

Ao lado do código testado (backup.test.ts junto de backup.ts). Dois projetos no
vitest.config.mts:
- main: src/main/**/*.test.ts e src/shared/**/*.test.ts, ambiente Node, banco SQLite real (em
  memória ou numa pasta temporária apagada no fim);
- renderer: src/renderer/**/*.test.{ts,tsx}, ambiente jsdom com Testing Library.

Testes da tela com o main de verdade (desde a etapa 2): src/renderer/src/test/realApi.ts monta
o window.mello com as mesmas rotas do main (routes.ts: Zod + módulos) sobre um SQLite em
memória. Só o transporte do Electron fica de fora; entradas e respostas passam por
structuredClone, como no IPC. Assim um teste de tela também confere o contrato com o banco.

Arquivos (desde a etapa 5): src/main/modules/test-files.ts cria uma pasta temporária com a pasta
de arquivos e um SystemPort falso: a janela "Abrir" devolve os caminhos que o teste combinou, e
abrir ou mostrar na pasta só ficam anotados; a janela de escolher pasta (etapa 10) devolve o que o
teste pôs em folders. O realApi.ts usa o mesmo, e um File "solto" no modal
só tem caminho se o teste o registrar (dropPath), como o webUtils do preload faria. Para digitar
na nota, os testes usam o editor que o TipTap pendura no elemento do texto.

O jsdom não tem o popover nem o <dialog> modal, que o app usa nativos. src/renderer/src/test/
setup.ts imita o mínimo, só nos testes: abrir e fechar, o evento "toggle", o botão com
popovertarget e o modal fechando os popovers. O arrastar com o mouse não funciona no jsdom (lá
tudo mede 0 px): ele é conferido no app real (seção 5), e as contas de onde o card cai são
testadas em funções puras (cardDrag.test.ts). O arrastar de cards pelo teclado roda no jsdom e é
testado na tela (BoardCards.test.tsx).

Calendário (desde a etapa 7): os testes da tela fixam "hoje" trocando só o Date
(vi.useFakeTimers({ toFake: ['Date'] })), e os temporizadores continuam de verdade. Como no jsdom
tudo mede 0 px (e então todos os itens cabem no dia), o "+N mais" é testado com medidas falsas
num teste só, além da função pura (visibleCount), e conferido no app real mudando o tamanho da
janela.

Limites de tempo dos testes da tela (desde a etapa 3): 5 s para os findBy… e o expect.poll e
20 s por teste. Cada teste monta o app inteiro com o banco de verdade, e os limites padrão (1 s e
5 s) estouravam às vezes com o computador ocupado, inclusive na versão da etapa 2. Um teste que
falha de verdade continua falhando; só demora mais para avisar.

Os testes da tela importam código do main, por isso têm o tsconfig.test.json próprio (com os
tipos do Node); o código da tela continua no tsconfig.web.json, sem acesso ao Node.

Os nomes dos testes citam o código da regra do Regras.txt quando existe (ex.: "DAD-01: …").

4. CONFERÊNCIA VISUAL E PONTA A PONTA (npm run capturas)

O script scripts/capturar-telas.mts compila o app, abre o Electron com uma pasta de dados
temporária (MELLO_DATA_DIR) e:
1. confere que o banco foi criado e que o IPC responde (app:info);
2. cria dados fictícios pelo window.mello, inclusive nota, anexos e capa (as fotos são
   gradientes desenhados no canvas, e a janela "Abrir" do Windows é trocada por uma que devolve
   esses arquivos);
3. salva uma captura de cada tela da etapa, nos temas escuro e claro, em capturas/etapa-N/
   (pasta ignorada pelo Git), inclusive com um card no meio do arraste;
4. desde a etapa 6, numa fase final, adianta o relógio de teste pelo atalho (Ctrl+Alt+→) e mexe
   em cada card num dia diferente, para os 5 níveis do envelhecimento aparecerem; o selo do
   relógio sai numa captura própria e fica escondido nas outras;
5. desde a etapa 8, a mesma fase deixa uma série semanal em aberto, para o aviso de pulada e as
   repetições tracejadas do calendário aparecerem; a notificação do Windows é trocada por uma
   anotação no main (nada aparece na tela), e o script lista os lembretes que dispararam e falha
   se nenhum disparou;
6. desde a etapa 8, encerra o app como o "Sair" da bandeja, cria dois lembretes de ontem e abre
   o app de novo com os mesmos dados: captura o aviso dos lembretes perdidos, fecha a janela
   para o aviso da bandeja e confere que o "Entendi" deixa a janela escondida;
7. desde a etapa 9, antes da fase final, desenha uma foto em retrato (o céu e as montanhas do
   protótipo, 1080 × 1920), envia pelo editor de fundo com a janela "Abrir" trocada, captura o
   editor (gradiente, cor, imagem com o ajuste automático e o ajuste à mão), aplica a foto no
   quadro "Casa" e captura o quadro, o calendário do quadro e o Início. A leitura dos pixels passa
   pelo protocolo de verdade (com CORS); o script mostra no terminal o ajuste calculado;
8. desde a etapa 10, troca o tema pela configuração de verdade em todas as telas (o Playwright
   abre o Electron sem a emulação de tema, que forçaria o claro) e captura as Configurações
   (telas 7 e 15) nos dois temas, com o rádio da própria tela; confere que "Igual ao sistema"
   segue o Windows, exporta para uma pasta (a janela é trocada; o Explorer só fica anotado),
   troca a pasta de backup e a apaga para ver o aviso; no fim, restaura um backup e apaga tudo
   de verdade (a reabertura do app vira só sair, e o script abre de novo e confere o resultado);
9. apaga a pasta temporária.

O Electron do script abre com opções do Chromium que mantêm a janela desenhando mesmo coberta ou
com o monitor desligado pelo Windows; sem elas, a captura podia esperar um quadro que não chegava
(visto na etapa 5). Cada captura tem três tentativas.

As capturas são comparadas com o .dc.html correspondente do protótipo (cores, medidas, textos,
ícones e estados). Numa tela com escala de 125% do Windows, a captura sai 1,25 vez maior
(1800 × 1125 para uma janela de 1440 × 900).
